# 繁殖予定の共通化: 第1段階

## この変更で行うこと

`client/src/utils/breedingPlans.ts` に、受け取った記録から表示用の予定と要確認事項を返す純粋な処理を追加する。データの読込・保存・同期・削除・予定完了処理は行わない。

この段階では既存画面から呼び出さない。既存の画面、記録、経費、ET実施時の保存処理、予定管理の完了状態は変わらない。共通処理のテストが通っても、複数画面の予定連動を修正済みとは扱わない。

## 入力の契約

- `projectBreedingPlans` は、対象牛と現在の繁殖周期が確定した1記録を受け取る。農場全体の配列から現在の周期を選ぶ処理ではない。
- `projectPostCalvingHeat` には、同じ牛と確認できた繁殖記録だけを渡す。同名の別個体を名前だけで混ぜてはいけない。
- `today` は、画面で使用する現地の暦日を明示して渡す。処理の内部で現在時刻を取得しない。
- `latestCalvingDate` は、対象牛の直近の実分娩日。予定日を渡さない。
- `plans` が空でも `issues` があれば「予定なし」と表示してはいけない。不明・不正・矛盾を確認する表示が必要。
- `date` がない案内を、`relatedDate` の日に実施する予約として扱わない。後者は関連する分娩日等の説明用。

## 判定の基本

| 記録の状態 | 表示用の候補 |
| --- | --- |
| 分娩後、後続活動なし | 日付を確定しない分娩後の発情確認 |
| 発情だけ記録 | 日付を確定しない種付方法の確認 |
| ET予定、未実施 | ET実施予定。妊娠鑑定や分娩を先に確定しない |
| 授精・ET実施、未鑑定 | 次回発情確認と妊娠鑑定 |
| 受胎・妊娠 | 分娩予定。既存の60日前基準内では増し飼い検討を日付なしで併記 |
| 空胎・不受胎 | 次回発情確認 |
| 再鑑定予定 | 再鑑定。日付不明でも作業自体を消さない |
| 分娩済み・中止 | その周期の未実施予定は出さない |
| 不正日付・矛盾・未対応の結果 | 要確認事項を返す。別の状態へ勝手に読み替えない |

AIの保存済み予定日は保持し、欠けている場合だけ既存の計算を使用する。ETは、これまで合意した発情日基準を表示に使う。発情日がないETを、移植日基準へ黙って戻してはいけない。既存レコードは書き換えない。

全予定の候補生成と、近日の表示期間は分離する。`upcomingBreedingPlans` は期限超過の未解決候補を7日経過だけで落とさない。`calendarBreedingPlans` は日付のある候補のみ返す。既存画面の「要対応」絞り込みへの適用条件は、接続時に照合する。

## テストの範囲

分娩後34日の案内、発情からET予定・実施・鑑定・分娩までの入力スナップショット変更、再鑑定・鑑定取消・移植取消、日付変更、記録が取り除かれた場合の再判定、ETの発情日基準、AIの保存済み予定日保持、日付境界、旧フィールド名、欠損・矛盾・未来の実績日、入力オブジェクトの不変性を検証する。

これらは純粋関数のテストであり、実画面で保存・取消・削除した結果の連携テストではない。取消・削除は、呼出元が更新済みの記録を渡すことを前提とする。

## 次の段階で必要なこと

1. 個体の識別と現在の周期選択を検証する。ID・耳標の矛盾、同名の別牛、旧記録、複数周期、販売済み、取得失敗や不完全データを「予定なし」にしない条件を固める。
2. 同じ記録セットを使う読み取り経路を確認し、個体カルテと台帳から段階的に接続する。既存の手動予定・治療・出荷などは別の候補として維持する。複数画面の照合テストを追加する。
3. ホーム、月間カレンダー、予定管理、TodayTasksへ順に広げる。予定管理に派生候補を出す際は、元記録に戻る導線と、手動予定の編集・削除を混同しない。
4. ET予定は繁殖記録と予定管理に別々に作られるため、作成元と対象を確実に特定できる連携方法を別途実装・検証する。タイトル・牛名・メモが似ているというだけで予定を非表示、削除、完了にしない。
5. 通常ET実施時など、保存経路に残る移植日基準の計算を、表示の統一とは別に修正・検証する。新規保存の修正と既存データの一括書換えは分ける。

## リリース確認

変更差分が共通処理・テスト・この文書だけであることを確認し、client/serverのテストとbuildを実行する。既存画面への接続、公開サイトへの更新、ユーザー端末での実表示確認は、それぞれ別の到達点として報告する。
