# 販売精算 Standard / Pro クラウド保存：統合判定

対象：PR #754 の検証ブランチのみ。**本番適用・有料保存解放は禁止**（以下が全部確認されるまで）。

## 既存実装から確認した事実
- `client/src/services/manualSettlementSave.ts`：Freeでは IndexedDB の expenses / metadata を同じトランザクションで保存。有料プランは fail-closed。
- `server/src/settlementSyncStore.ts`：農場別 `settlement-sync.json` に精算と新規経費スナップショットを一括記録。既存経費の通常同期ストアとは別ファイル。
- `server/src/expenseSyncStore.ts`：通常の経費一覧は `expenses-sync.json` を使用。**精算スナップショットは通常経費一覧に自動的には反映されない**。
- `server/src/routes/expenses.ts`：クラウド精算状態・詳細の読み取り専用APIを持つ。精算確定POSTはまだない。

## 完成に必要な実装（順番を厳守）
1. **クラウドを正本にする一括確定API**：認証済み農場内で販売済み状態・対象牛・金額・控除合計・既存経費リンクをサーバーが再照合する。クライアントの金額や既存経費IDを無条件に信頼しない。
2. **精算と経費一覧が矛盾しない保存モデル**：二つのJSONへ個別書き込みする方式を採用しない。単一原子的記録を正本とし、通常経費一覧への公開を同じ正本から生成する等の設計を決定する。再起動後も一貫して読めること。
3. **同時登録・通信断・再送のテスト**：同じ販売への同時要求、応答喪失後の再送、別端末からの読み取りを検証。二重登録・二重計上・部分保存を0件にする。
4. **既存記録との互換性**：FreeのIndexedDB記録、Standard/Proの既存経費、既存経費の紐づけ、削除済み記録の扱い、別農場への漏出がないことを確認。
5. **検証環境で実機試験**：二端末・二農場・ログアウト/再ログイン・通信断を実施。実利用者データを使わない。
6. **本番判断**：上記完了・CI成功・利用者確認後にのみ、明示承認を得てマージする。

## 現在の結論
読み取り表示と重複検査の基礎はあるが、精算の経費が通常の経費同期に現れることは保証されない。現時点で有料の保存ボタンを有効化しない。
