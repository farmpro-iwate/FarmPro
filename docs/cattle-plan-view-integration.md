# 繁殖予定の共通化: 第2段階（台帳・個体カルテ）

## 対象

`CattleList` と `CattleDetail` の自動生成される繁殖予定を、同じ `getCattlePlanSnapshot` → `resolveCattleBreedingPlans` → `CattleBreedingPlanItems` に接続する。

第1段階の `breedingPlans.ts` は1頭の現在周期が既に確定した入力を前提としていた。今回は対象牛の識別と現在周期の選択、読込失敗の表示、2画面への接続を追加する。

## 保持するもの

- 保存済みレコードの内容・ID・タイムスタンプ。
- 既存の保存・削除・同期ポリシー、経費計算と販売時原価。
- ET実施画面の保存処理（発情日基準への保存経路修正は別工程）。
- 予定管理の完了状態と手動予定。表示によって完了・取消・削除しない。
- 個体カルテの個体ストーリー・産歴・生産費・子牛等の表示。
- 個体カルテの既存の手動予定・再診・出荷予定の抽出条件。繁殖予定と別に併記する。

## 予定の判定

- IDまたは耳標番号を使う。牛名だけでは結び付けず、矛盾する識別情報は警告する。
- 実分娩日前の繁殖周期を、新しい更新日時や鑑定日の編集だけで復活させない。
- 現周期の選択は発情日・実施日・明示されたET予定に基づく。複数の同周期サービスや、受胎記録と新しい繁殖活動の重複は確認を求める。
- 最新周期が分娩済み・中止の場合、その記録を単に除外して古い未完了周期へ戻らない。
- 発情だけの別記録と、同じ発情日に紐づく1件の実施記録は、実施記録を表示判定に用いる。保存データを統合する処理ではない。
- ETの派生表示日は発情日基準。保存されている旧推定日を書き換えない。
- 台帳は先の予定も表示し、「要対応のみ」の期間条件とは切り離す。
- 増し飼い検討は日付なしの継続案内とし、分娩予定日は関連日として明記する。
- 日付未登録・不正・周期不明・取得失敗がある場合は「予定なし」と断定しない。

## 読み込みと同期の限界

両画面は同じ既存リーダーを1回ずつ呼ぶ。繁殖記録・販売記録・農場設定・端末内の分娩記録をまとめて扱い、上位に伝わった読み取りエラーや不正な取得形式を表示する。

既存リーダー内部でクラウド取得の失敗が処理され、端末内データに戻る場合のポリシーは変えない。この変更はクラウドの最新性・複数端末間の同期完了を保証するものではない。

## 検証

- `cattleBreedingPlans.test.ts`: 個体識別、同名別牛、矛盾、現周期、旧記録、分娩・中止の境界、欠損・不正、入力不変性、予定と要対応条件の分離。
- `CattlePlans.shared-view.test.tsx`: 同じ取得スナップショットを実際の台帳・個体カルテのコンポーネントへ渡し、予定の種類・日付を固定した期待値と比較する。記録変更・鑑定取消・削除後の再読込、取得失敗、手動作業・原価の保持も確認する。
- `CattlePlans.storage-flow.test.tsx`: 外部通信を禁止した `fake-indexeddb` 上で、実際のrepositoryと繁殖保存・更新・削除サービスを使用し、保存後に両画面を再度開いて比較する。表示前後で保存データが変化しないことも確認する。利用者の実データや実端末を操作するテストではない。
- 既存の次回予定テストは農場設定のモックを明示する。受胎牛の回帰テストは、直近分娩後の実施日を明示した入力にする。周期不明の受胎記録は別テストで警告を確認する。既存の期待値を削除して成功扱いにはしない。

clientとserverの全体テスト・buildが最終headで成功し、既存ファイルの差分を確認するまでマージしない。

## 次工程・未完了

ホーム、TodayTasks、月間カレンダー、予定管理にはまだ接続しない。繁殖記録と別に作られたET予定の完了連携や、ET実施保存時の日付基準は別途修正が必要。

個体ストーリー等の旧来の識別処理や「今の状態」の全面的な共通化はこの変更の対象外。今回確認するのは自動繁殖予定の一致であり、全表示・全履歴が統一済みとは報告しない。

本線へのマージ、公開デプロイ、利用者端末での表示確認はそれぞれ別に記録する。
